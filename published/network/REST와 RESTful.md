> [REST는 리소스를 URI로 식별하고 HTTP 메서드로 행위를 표현하는 아키텍처 스타일이며, RESTful은 그 원칙을 비교적 잘 따르는 API를 가리키는 표현이다.]{.lead}

## 정의
- [REST]{.term}는 Representational State Transfer의 줄임말로, 네트워크에서 리소스를 중심으로 상호작용하도록 제안된 아키텍처 스타일이다.
- [리소스]{.term}는 API가 다루는 대상이다. 예를 들어 사용자, 게시글, 댓글 같은 명사는 URI로 식별하고, 행위는 HTTP 메서드로 표현한다.
- [Representation]{.term}은 리소스의 현재 상태를 JSON, HTML, XML 같은 형태로 표현한 결과다. 클라이언트는 리소스 자체가 아니라 표현을 주고받는다.
- [RESTful]{.term}은 REST 제약을 비교적 잘 따르는 API를 가리키는 표현이다. 절대적인 인증 마크라기보다 설계 원칙을 얼마나 일관되게 지키는지에 가까운 말이다.
- [무상태성]{.term}은 서버가 이전 요청의 문맥에 의존하지 않고, 각 요청만으로 필요한 정보를 이해할 수 있어야 한다는 제약이다.
- [계층화]{.term}는 클라이언트가 중간 프록시, 게이트웨이, 캐시 같은 계층을 직접 의식하지 않아도 통신할 수 있게 하는 구조적 제약이다.
- REST API는 HTTP를 자주 활용하지만, [REST 자체가 HTTP와 완전히 같은 뜻은 아니다.]{.warning}

## 핵심 포인트
- [REST는 규격보다 설계 스타일에 가깝다.]{.accent} 그래서 완벽한 정답 하나보다 원칙을 일관되게 적용하는지가 중요하다.
- URI는 행위보다 [리소스 이름]{.term}을 표현하는 것이 자연스럽다. 예를 들어 createUser보다 users처럼 대상 중심으로 설계한다.
- [GET]{.term}은 조회, [POST]{.term}는 생성이나 처리 요청, [PUT]{.term}은 전체 교체, [PATCH]{.term}는 일부 수정, [DELETE]{.term}는 삭제에 대응시키는 경우가 많다.
- CRUD를 URI에 동사로 넣기보다 [HTTP 메서드가 행위를 표현하게 하는 것]{.accent}이 REST 스타일에 더 가깝다.
- 상태 코드는 응답 의미를 드러내는 중요한 신호다. 성공은 2xx, 클라이언트 오류는 4xx, 서버 오류는 5xx 계열로 구분한다.
- 무상태성 덕분에 서버는 요청 사이의 사용자 문맥을 직접 붙잡지 않아도 된다. 이 특성은 서버 확장과 장애 대응을 단순하게 만드는 데 도움이 된다.
- 캐시 가능 응답은 Cache-Control 같은 헤더로 명시할 수 있다. 조회 응답을 적절히 캐시하면 성능과 트래픽 효율을 높일 수 있다.
- [RESTful이라는 표현은 상대적이다.]{.warning} 실무 API는 보안, 성능, 도메인 요구 때문에 순수한 REST보다 일관성과 명확성을 우선할 때도 있다.
- [REST API라고 해서 인증, 권한, 입력 검증이 자동으로 해결되는 것은 아니다.]{.danger}

## 면접 질문
- REST와 RESTful을 설명해보세요.
- 좋은 REST API 설계의 기준은 무엇인가요?
- URI와 HTTP 메서드는 각각 무엇을 표현해야 하나요?
- REST의 무상태성은 서버 확장에 어떤 도움을 주나요?
- RESTful API에서 상태 코드를 적절히 쓰는 것이 왜 중요한가요?
- RESTful이라는 표현을 절대적인 기준처럼 보기 어려운 이유는 무엇인가요?

## 확인 문제
- REST는 리소스 중심 설계와 관련이 있을까?
- RESTful은 완벽한 정답 여부만 가르는 단어일까?
- URI에는 리소스를, HTTP 메서드에는 행위를 담는 것이 자연스러울까?
- 무상태성은 각 요청이 필요한 정보를 스스로 포함해야 한다는 의미일까?
- GET 요청은 일반적으로 조회에 사용될까?
- 상태 코드는 응답 결과의 의미를 클라이언트에 전달하는 단서일까?
- REST API도 인증과 권한 검사가 별도로 필요할까?
