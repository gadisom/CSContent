> [브라우저에 URL을 입력하면 DNS 조회, 연결 수립, TLS 핸드셰이크, HTTP 요청, 서버 처리, 응답 렌더링이 이어지며 하나의 웹 페이지가 화면에 나타난다.]{.lead}

## 정의
![[web-request-flow.png]]

- [URL 해석]{.term}: 브라우저는 사용자가 입력한 문자열을 URL로 해석하고, 프로토콜, 도메인, 경로, 쿼리 같은 구성 요소를 나눈다.
- [캐시 확인]{.term}: 브라우저는 HTTP 캐시, DNS 캐시, 연결 재사용 가능성 등을 먼저 확인해 네트워크 요청을 줄일 수 있는지 판단한다.
- [DNS 조회]{.term}: 도메인 이름을 실제 서버 IP 주소로 바꾸는 단계다. 캐시에 없으면 재귀 해석기를 통해 권한 있는 네임서버까지 조회할 수 있다.
- [TCP 연결]{.term}: HTTP/1.1이나 HTTP/2에서는 보통 서버와 TCP 연결을 맺고, 3-way handshake로 양쪽의 송수신 가능성을 확인한다.
- [TLS 핸드셰이크]{.term}: HTTPS라면 TCP 연결 위에서 서버 인증서 확인과 키 교환을 수행하고, 이후 데이터를 보호할 세션 키를 만든다.
- [HTTP 요청]{.term}: 브라우저는 메서드, 경로, 헤더, 쿠키 등을 포함한 HTTP 요청을 서버로 보낸다.
- [서버 처리]{.term}: 서버는 라우팅, 인증, 비즈니스 로직, 데이터베이스 조회 등을 거쳐 HTTP 응답을 만든다.
- [렌더링]{.term}: 브라우저는 HTML을 파싱하고 CSS, JavaScript, 이미지 같은 추가 리소스를 요청하며 화면을 구성한다.

## 핵심 포인트
- [웹 요청은 하나의 동작처럼 보여도 여러 계층 단계가 이어진 결과]{.accent}다.
- DNS는 목적지 IP를 찾고, TCP는 안정적인 연결을 만들며, TLS는 통신 구간을 보호하고, HTTP는 애플리케이션 요청과 응답의 의미를 표현한다.
- HTTPS 요청에서는 보통 [DNS → TCP 3-way handshake → TLS handshake → HTTP request → HTTP response]{.accent} 흐름으로 이해할 수 있다.
- 이미 열려 있는 연결을 재사용하거나 캐시가 적중하면 일부 단계는 생략되거나 짧아질 수 있다.
- HTTP 요청에는 쿠키, 인증 헤더, Accept 헤더, User-Agent 같은 메타데이터가 포함될 수 있다.
- 서버 응답은 상태 코드, 헤더, 본문으로 구성된다. 브라우저는 상태 코드와 헤더를 보고 캐시, 리다이렉트, 쿠키 저장 같은 동작을 결정한다.
- HTML 응답을 받았다고 화면이 즉시 완성되는 것은 아니다. CSS, JavaScript, 이미지, 폰트 같은 하위 리소스 요청이 추가로 발생할 수 있다.
- [CORS는 서버 간 통신 문제가 아니라 브라우저가 응답을 프론트엔드 코드에 노출할지 판단하는 정책과 관련된다.]{.warning}
- 장애를 추적할 때는 DNS 실패, 연결 실패, TLS 인증서 문제, HTTP 상태 코드, 프론트엔드 렌더링 오류를 단계별로 나누어 보면 원인을 좁히기 쉽다.

- 캐시가 적중하면 일부 네트워크 요청을 줄일 수 있을까?

- HTML 안의 이미지나 CSS 때문에 추가 요청이 발생할 수 있을까?
- CORS는 브라우저가 응답 노출 여부를 판단하는 정책과 관련 있을까?
