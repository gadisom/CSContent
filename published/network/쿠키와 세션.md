> [쿠키는 브라우저가 저장하고 요청에 함께 보낼 수 있는 데이터이고, 세션은 서버가 사용자 상태를 관리하는 방식이다. 둘은 대체 관계보다 함께 쓰이는 경우가 많다.]{.lead}

## 정의
- [HTTP]{.term}는 기본적으로 이전 요청 상태를 기억하지 않는 무상태 프로토콜이다. 로그인 상태처럼 요청 사이에 유지되어야 하는 정보는 별도의 상태 관리 방식이 필요하다.
- [쿠키]{.term}는 브라우저에 저장되고, 조건이 맞으면 같은 도메인 요청에 자동으로 함께 전송될 수 있는 작은 데이터다.
- [세션]{.term}은 서버가 사용자 상태를 관리하는 방식이다. 보통 브라우저에는 세션 자체가 아니라 [세션 ID]{.term}만 쿠키로 저장하고, 실제 사용자 정보는 서버에 둔다.
- [Set-Cookie]{.term}는 서버가 브라우저에 쿠키 저장을 요청할 때 사용하는 응답 헤더다.
- [Cookie]{.term} 헤더는 브라우저가 저장된 쿠키를 서버 요청에 함께 보낼 때 사용한다.
- [HttpOnly]{.term}는 JavaScript에서 쿠키에 접근하지 못하게 하는 속성이고, [Secure]{.term}는 HTTPS 요청에서만 쿠키가 전송되도록 하는 속성이다.
- [SameSite]{.term}는 다른 사이트에서 시작된 요청에 쿠키를 함께 보낼지 제한하는 속성이다. CSRF 같은 공격 위험을 줄이는 데 도움을 준다.

## 핵심 포인트
- [쿠키는 저장 위치와 전달 방식, 세션은 서버 측 상태 관리 방식]{.accent}에 가깝다.
- 세션 기반 로그인에서는 서버가 세션을 만들고, 클라이언트는 세션 ID가 담긴 쿠키를 이후 요청마다 함께 보낸다.
- [쿠키에 민감한 사용자 정보를 직접 넣는 것은 위험하다.]{.danger} 쿠키에는 보통 식별자나 제한된 정보만 두고, 중요한 상태는 서버에서 관리한다.
- 세션은 서버 메모리나 저장소를 사용하므로 사용자가 많아지면 저장 위치, 만료 정책, 서버 간 공유 방식을 고려해야 한다.
- 분산 서버 환경에서는 세션을 특정 서버 메모리에만 두면 요청이 다른 서버로 갔을 때 상태를 찾지 못할 수 있다. Redis 같은 중앙 저장소나 sticky session 같은 전략을 사용할 수 있다.
- 쿠키 보안 속성은 인증 흐름에서 중요하다. [HttpOnly, Secure, SameSite를 상황에 맞게 설정해야 한다.]{.warning}
- 세션 만료 시간은 보안과 사용자 경험의 균형을 잡아야 한다. 너무 길면 탈취 위험이 커지고, 너무 짧으면 사용성이 떨어진다.
- [쿠키와 세션은 경쟁 개념이 아니라 함께 조합되는 경우가 많다.]{.accent}

## 면접 질문
- 쿠키와 세션의 차이를 설명해보세요.
- 세션 기반 로그인은 어떻게 동작하나요?
- HTTP가 무상태라는 말은 무엇이고, 쿠키와 세션은 이를 어떻게 보완하나요?
- 세션 ID를 쿠키에 저장할 때 주의할 보안 속성은 무엇인가요?
- 서버를 여러 대로 늘릴 때 세션 관리에서 어떤 문제가 생길 수 있나요?

## 확인 문제
- 세션은 항상 브라우저에 직접 저장될까?
- 쿠키는 클라이언트 측 저장소 역할을 할 수 있을까?
- 세션 기반 인증에서는 세션 ID를 쿠키에 담아 보낼 수 있을까?
- HttpOnly 쿠키는 JavaScript 접근을 제한하는 데 도움이 될까?
- Secure 속성이 있는 쿠키는 HTTPS에서만 전송되도록 제한할 수 있을까?
- SameSite는 교차 사이트 요청에서 쿠키 전송을 제한하는 데 관련이 있을까?
- 쿠키와 세션을 함께 사용할 수 있을까?
