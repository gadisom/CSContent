> [값 타입과 참조 타입의 차이는 메모리 위치보다 값의 의미와 객체의 식별성을 어떻게 다루는지에 있다.]{.lead}

## 정의
- [값 타입]{.term}은 변수에 할당하거나 함수에 전달할 때 값이 복사되는 타입이다.
- Swift의 `struct`, `enum`, `tuple`, `Int`, `String`, `Array`, `Dictionary`는 대표적인 값 타입이다.
- [참조 타입]{.term}은 변수에 인스턴스 자체가 아니라 인스턴스를 가리키는 참조가 저장되는 타입이다.
- Swift의 `class`는 대표적인 참조 타입이며, 여러 변수가 같은 인스턴스를 함께 가리킬 수 있다.
- [Value Semantics]{.term}는 값이 같으면 같은 의미로 취급되고, 변경이 다른 값에 예상치 못한 영향을 주지 않는 성질이다.
- [Reference Semantics]{.term}는 객체의 값뿐 아니라 같은 객체인지, 언제 생성되고 해제되는지 같은 식별성과 생명주기가 중요한 성질이다.
- 값 타입 안에 class 인스턴스를 저장하면 겉은 값 타입이어도 내부 참조가 공유될 수 있다.
- [Copy-on-Write]{.term}는 값 타입 컬렉션이 저장소를 공유하다가 변경이 필요할 때만 복사하는 최적화 방식이다.
- 참조 타입의 생명주기는 [ARC]{.term}로 관리되며, 강한 참조가 남아 있으면 객체는 해제되지 않는다.

## 핵심 포인트
- [struct는 값의 의미, class는 객체의 식별성을 표현할 때 자연스럽다.]{.accent}
- 값 타입은 데이터 흐름을 예측하기 쉽지만, 내부에 참조 타입을 들고 있으면 완전한 독립성이 깨질 수 있다.
- 참조 타입은 동일성 비교, 상속, Objective-C 호환, 공유 mutable state, 긴 생명주기를 가진 객체에 적합하다.
- `let`으로 선언한 값 타입은 내부 값을 변경할 수 없지만, `let`으로 잡은 class 인스턴스는 참조 재할당만 막고 내부 `var` 프로퍼티 변경은 가능하다.
- SwiftUI의 View는 `struct` 기반 값 타입이며 자주 다시 만들어질 수 있다. 화면의 지속 상태는 `@State`, `@StateObject` 같은 저장소가 담당한다.
- Array나 Dictionary는 값 타입이지만 대입할 때마다 즉시 전체 복사하지 않고, 공유 저장소를 변경하려는 순간 Copy-on-Write로 분리한다.
- [값 타입을 선택했다면 내부 상태까지 정말 값처럼 동작하는지 확인해야 한다.]{.warning}
- [참조 타입은 여러 곳에서 같은 상태를 바꿀 수 있어 메모리 관리와 동시성 이슈를 더 신경 써야 한다.]{.danger}
- `===`는 class 인스턴스 두 참조가 같은 객체를 가리키는지 확인하는 동일성 비교다.
- `==`는 값이 같은지 비교하는 동등성 비교이며, 타입이 `Equatable`을 채택해야 사용할 수 있다.
- 공유 변경이 필요하지 않은 모델, 화면 상태 스냅샷, DTO는 값 타입이 어울리고, 사용자 세션처럼 하나의 정체성을 가진 객체는 참조 타입이 어울린다.

- 값 타입과 Value Semantics는 같은 말인가요?
- 값 타입 안에 class 프로퍼티가 있으면 어떤 문제가 생길 수 있나요?
- `struct는 stack, class는 heap에 저장된다`는 설명이 왜 부정확한가요?
- `let`으로 선언한 class 인스턴스의 프로퍼티를 변경할 수 있는 이유는 무엇인가요?
- Copy-on-Write는 왜 필요한가요?
- SwiftUI View가 struct인 이유를 값 타입 관점에서 설명해보세요.
- 동일성 비교 `===`와 값 비교 `==`는 어떻게 다른가요?
