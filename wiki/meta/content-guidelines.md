## 퀴즈 작성 기준

### 난이도 정의
- **beginner**: CS를 처음 배우는 사람도 이해 가능. 용어 정의, 기초 개념 확인.
- **intermediate**: 개념을 알고 적용할 수 있는지 확인. 비교, 선택 이유 묻기.
- **advanced**: 깊은 이해 요구. 트레이드오프, 엣지 케이스, 구현 세부 사항.

### 퀴즈 구조
```
문제: (질문)
①
②
③
④
정답: (번호)
해설: (왜 정답인지, 왜 오답인지 간략히)
```

### 좋은 퀴즈의 조건
- 하나의 핵심 개념에 집중한다.
- 오답도 그럴듯해야 한다 (단순 엉터리 X).
- 해설이 학습 가치를 가져야 한다.
- 빈칸 문제는 본문에 정답, 번역, 약어, 기호를 직접 노출하지 않는다. 예: `___(TLB)`, `192.168.0.0/24에서 /24는 ___`처럼 답이 문장 안에 보이는 형태 금지.
- 빈칸 답은 사용자가 한국어로 짧게 적을 수 있는 단일 용어를 묻는다. 영어 API명, 클래스명, 약어, 숫자만 맞히는 문제는 객관식으로 돌리거나 한국어 개념어를 묻도록 바꾼다.

## 개념 설명 작성 기준

### 구조
1. 한 줄 정의 (전문 용어 없이)
2. 직관적 비유 또는 예시
3. 기술적 상세 설명
4. 코드 예시 (해당하는 경우)
5. 관련 개념 링크

### 섹션별 문체
- `## 정의`에는 개념의 의미, 역할, 구성 요소만 적는다.
- `## 정의`와 `## 핵심 포인트`에는 `면접에서는`, `면접에선`, `인터뷰에서는`처럼 면접 상황을 직접 언급하는 문장을 넣지 않는다.
- 면접 답변 요령이나 답변 관점은 `## 면접 질문`의 질문으로 유도하거나, 별도 `면접 포인트` 섹션이 있는 wiki/concepts 문서에서만 다룬다.
- 앱에 노출되는 published 문서는 학습 설명 문체를 유지하고, 특정 시험/면접 상황을 전제로 한 조언 문체를 본문 개념 설명에 섞지 않는다.

### SDUI semantic token
- 앱 렌더링에서 의미 있는 강조가 필요하면 색상값이나 폰트 크기 대신 semantic token을 사용한다.
- 허용 토큰은 `{.accent}`, `{.danger}`, `{.success}`, `{.warning}`, `{.muted}`, `{.term}`, `{.lead}`, `{.caption}`이다.
- 용어 강조: `[TLS]{.term}`
- 핵심 강조: `[비대칭키는 안전한 키 교환에 쓰인다]{.accent}`
- 주의 강조: `[HTTPS가 모든 보안 문제를 해결하지는 않는다]{.warning}`
- 요약 강조: `> [핵심 요약 문장]{.lead}`
- 코드 백틱과 토큰 문법은 섞지 않는다. 금지: `` `[4-tuple]{.term}` ``. 허용: `[4-tuple]{.term}`.
- 토큰은 문서의 의미를 설명하기 위한 표시이며, 직접 색상이나 크기를 지시하지 않는다.
- 모든 단어를 꾸미지 말고, 핵심 용어와 오해하기 쉬운 문장 위주로 제한적으로 사용한다.

### 길이
- beginner: 300-500자
- intermediate: 500-800자
- advanced: 800자 이상 가능
